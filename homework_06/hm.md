## 1\. Сценарій і мета

ДЗ 1 з заняття `1.2` було балістичною задачею: за позицією дрона, позицією цілі, швидкістю атаки, дистанцією розгону і типом боєприпасу треба обчислити точку скиду.

У ДЗ 6 ця задача використовується як невеликий знайомий домен для повного робочого циклу перевірки якості:

- додати автоматичні тести;  
- перевірити форматування, попередження і статичний аналіз;  
- здати зміни через PR згідно з правилами курсу.

- CMake target для балістичної логіки;  
- CMake target для консольної програми;  
- CMake target для тестів з Google Test або іншим уже погодженим тестовим підходом;  
- тести зареєстровані у CTest.

## 5\. Тести

Очікуваний мінімум тестів:

- еталонний тест для прикладу з ДЗ 1;  
- тест для невідомого типу боєприпасу або некоректного вхідного файла.

Для еталонного тесту використати приклад вхідних і вихідних даних з ДЗ 1\.

Для чисел з рухомою комою не треба порівнювати текстовий вивід побайтно. Тест має порівнювати числа з розумним допуском.

Корисні додаткові тести:

- планеруючий боєприпас дає скінченний додатний час падіння;  
- невідомий `ammo_name` повертає контрольовану помилку;  
- висота `zd <= 0` або нульова відстань до цілі обробляється без аварійного падіння;  
- сценарій, де потрібна проміжна точка маневру.

### Мінімальний приклад тесту

Приклад нижче не є готовим розв'язком ДЗ 6\. Він показує форму: окремий CMake target для тестів, підключення до бібліотеки з доменною логікою і реєстрація у CTest.

Фрагмент `homework_06/CMakeLists.txt`:

add\_library(ballistics src/ballistics.cpp)

target\_include\_directories(ballistics PUBLIC include)

add\_executable(ballistics\_cli src/main.cpp)

target\_link\_libraries(ballistics\_cli PRIVATE ballistics)

if(NOT CMAKE\_CROSSCOMPILING)

  include(FetchContent)

  include(GoogleTest)

  FetchContent\_Declare(

      googletest

      URL https://github.com/google/googletest/archive/refs/tags/v1.14.0.zip

      DOWNLOAD\_EXTRACT\_TIMESTAMP TRUE

  )

  FetchContent\_MakeAvailable(googletest)

  add\_executable(ballistics\_tests tests/ballistics\_tests.cpp)

  target\_link\_libraries(ballistics\_tests PRIVATE ballistics GTest::gtest\_main)

  gtest\_discover\_tests(ballistics\_tests DISCOVERY\_MODE PRE\_TEST)

endif()

Якщо Google Test уже підключено в кореневому `CMakeLists.txt`, блок `FetchContent` не треба дублювати у `homework_06/CMakeLists.txt`.

Блок `if(NOT CMAKE_CROSSCOMPILING)` потрібен, щоб ARM64 cross-build збирав програму і бібліотеку, але не намагався запускати тестовий executable іншої архітектури під час GoogleTest discovery.

Мінімальний тест у `homework_06/tests/ballistics_tests.cpp`:

\#include "ballistics.hpp"

\#include \<gtest/gtest.h\>

TEST(Ballistics, ComputesKnownDropPoint) {

  const BallisticsInput input{

      .drone\_x \= 100.0,

      .drone\_y \= 100.0,

      .drone\_z \= 100.0,

      .target\_x \= 200.0,

      .target\_y \= 200.0,

      .attack\_speed \= 10.0,

      .acceleration\_path \= 10.0,

      .ammo\_name \= "VOG-17",

  };

  const DropSolution solution \= compute\_drop\_solution(input);

  EXPECT\_NEAR(solution.fire\_x, 173.759, 0.01);

  EXPECT\_NEAR(solution.fire\_y, 173.759, 0.01);

}

Назви `BallisticsInput`, `DropSolution` і `compute_drop_solution` умовні. У власному коді вони можуть називатися інакше. Важлива ідея: тест викликає функцію з бібліотеки напряму і перевіряє поведінку, а не просто факт запуску програми.

## 6\. Форматування

C++ файли:

clang-format \-i homework\_06/include/ballistics.hpp \\

  homework\_06/src/ballistics.cpp \\

  homework\_06/src/main.cpp \\

  homework\_06/tests/ballistics\_tests.cpp

CMake файли:

cmake-format \-i homework\_06/CMakeLists.txt

Якщо структура файлів інша, треба застосувати інструмент форматування до фактично змінених C++ і CMake-файлів.

Важливо:

- не робити випадкове наведення форматування всього репозиторію в одному PR з ДЗ 6, якщо це створює велику непов'язану різницю змін;  
- у кореневому `CMakeLists.txt` достатньо додати тільки потрібні рядки для `homework_06`; якщо `cmake-format` переформатував старі коментарі або чужі блоки, такий шум не треба залишати в PR;  
- не виправляти стиль вручну там, де інструмент форматування може зробити це автоматично;  
- не комітити артефакти збірки після запуску інструментів форматування, збірки або тестування.

## 7\. Попередження компілятора

Очікування:

- не потрібно самостійно вигадувати новий набір прапорців компілятора;  
- не потрібно самостійно вмикати `-Werror`, якщо цього немає в шаблоні репозиторію;  
- використовується те, що вже налаштовано в CMake-файлах курсу або власного репозиторію;  
- якщо збірка показує попередження у зміненому коді, його треба прочитати і або виправити, або свідомо залишити тільки з очевидною причиною.

Типові попередження, які треба виправляти:

- unused variable;  
- missing return у non-void function;  
- signed/unsigned comparison;  
- shadowed variable;  
- unused function або unused include, якщо вони з'явилися під час роботи.

## 8\. Статичний аналіз через `clang-tidy`

У ДЗ 6 не треба підбирати власний великий список перевірок `clang-tidy`. Запускати `clang-tidy` потрібно з наявною конфігурацією репозиторію або з конфігурацією, показаною на лекції.

У devcontainer `clang-tidy` встановлено, але він не запускається автоматично під час `cmake --build`. Це окрема команда для ручної перевірки змінених файлів.

Мінімальний запуск:

clang-tidy \-p build/debug homework\_06/src/ballistics.cpp

clang-tidy \-p build/debug homework\_06/src/main.cpp

clang-tidy \-p build/debug homework\_06/tests/ballistics\_tests.cpp

Якщо доступний `run-clang-tidy`:

run-clang-tidy \-p build/debug homework\_06

Що треба зробити із зауваженнями:

- прочитати назву перевірки і повідомлення;  
- виправити очевидні bugprone/analyzer/performance зауваження;  
- стильові/naming зауваження не є головною ціллю ДЗ 6, якщо вони не маскують реальну проблему;  
- не робити механічні зміни, якщо зауваження потребує контексту;  
- `NOLINT` використовувати тільки точково і з короткою причиною.

## 9\. Частина B: зручний робочий процес

Потрібно додати одну зручну точку входу для команд перевірки якості.

Допустимі варіанти:

- `Makefile`;  
- shell-скрипт, наприклад `scripts/check-quality`;  
- завдання (Tasks) VS Code.

Рекомендовані команди:

Або еквівалент через скрипти/завдання.

Важливо: оцінюється не сама обгортка, а повторюваність. Має бути зрозуміло, яку одну команду запускати перед PR.

## 10\. Частина C: додаткова автоматизація

Це необов'язкова частина для тих, хто хоче піти ще далі в покращенні якості.

Можливі варіанти:

- pre-commit hook для `clang-format`;  
- робочий процес GitHub Actions, який запускає збірку і тести;  
- окремий крок CI для `clang-tidy` на змінених файлах;  
- шаблон PR з контрольним списком перевірки.

Додаткова автоматизація не має ламати базову здачу. Якщо автоматизація нестабільна, краще описати її як експеримент і не блокувати основний PR.

## 12\. Критерії оцінювання

Основні критерії:

- `homework_06` (або інша назва папки з ДЗ) збирається через CMake preset;  
- доменна логіка винесена в окремий CMake target;  
- тести запускаються через CTest;  
- є принаймні один еталонний тест і один негативний або помилковий сценарій;  
- інструмент форматування застосовано до змінених файлів;  
- нові попередження компілятора у зміненому коді не ігноруються;  
- `clang-tidy` запущено з наявною конфігурацією, очевидні зауваження опрацьовані;  
- різниця змін не містить непов'язаного наведення форматування або артефактів збірки.

## 13\. Типові помилки

- `homework_06` додано, але не підключено до CMake з кореня репозиторію;  
- тести написані, але не зареєстровані у CTest;  
- тест перевіряє лише факт запуску виконуваного файла, а не результат розрахунку;  
- числа з рухомою комою порівнюються як точний текст без допуску;  
- `clang-format` застосовано до всього репозиторію і PR став нечитабельним;  
- попередження приглушено без пояснення;  
- `NOLINT` додано без причини;  
- директорія `build` або згенеровані файли потрапляють у commit;
